# Nodryl — Product Plan

## 1. Product Name

**Nodryl**

### Working tagline
> **Watch your software run.**

Alternative taglines:
- **Architecture in motion.**
- **See what your system is doing.**
- **Understand software by watching it happen.**
- **A live visual debugger for software systems.**
- **See the system behind the code.**

---

# 2. Product Vision

Nodryl is a **terminal-first live visual system explorer** that lets developers see how their software architecture behaves in real time.

Instead of showing only code, logs, traces, or a static architecture diagram, Nodryl creates a **living visual representation of the system**.

Developers can watch:

- API requests move through the system
- services communicate with each other
- database queries execute
- queues receive and process events
- external APIs get called
- authentication flows happen
- background workers activate
- errors propagate
- retries happen
- latency accumulate
- AI/LLM calls occur
- frontend actions trigger backend behavior

The goal is simple:

> **Developers should be able to understand a system by watching it run.**

Nodryl is especially relevant in a world where developers increasingly use AI coding tools and may not fully understand every part of the code being generated.

---

# 3. The Problem

Modern software systems are becoming harder to mentally understand.

A developer may be working with:

- dozens of API routes
- multiple services
- databases
- caches
- queues
- background jobs
- external APIs
- authentication systems
- cloud infrastructure
- AI services
- code generated by AI agents

Traditional development tools expose these pieces separately.

For example:

- IDE → code
- logs → text output
- debugger → individual execution state
- observability platform → traces and metrics
- architecture diagram → manually maintained structure
- Git → file changes
- APM → production performance

But developers still have to build the **mental model of the system themselves**.

This becomes even more difficult with AI-assisted development.

A developer can ask an AI agent:

> “Add payments, retries, Redis caching, and a background worker.”

The AI may modify many files and introduce several architectural elements.

The application may work.

But the developer may no longer fully understand:

- what was added
- how things connect
- what happens during a request
- where data travels
- which services depend on each other
- what might break if something changes

Nodryl exists to solve this problem.

---

# 4. Core Product Philosophy

Nodryl is not primarily an architecture diagram generator.

It is not a dashboard.

It is not simply an observability platform.

It is not just a debugger.

It is a **live visual model of software execution**.

The core idea:

> **Do not visualize architecture. Visualize software happening.**

# 5. Primary Goals

Nodryl should solve three major problems.

## 5.1 Understand

Help developers quickly understand:

- what exists in the system
- how components are connected
- how APIs work
- where data flows
- which services depend on each other
- what infrastructure is involved
- how a feature is implemented

Typical use cases:

- opening an unfamiliar repository
- joining a new engineering team
- exploring an open-source project
- reviewing AI-generated code
- understanding a legacy system
- onboarding junior developers

---

## 5.2 Learn

Nodryl should help developers learn software architecture using **real software instead of abstract diagrams**.

A developer should be able to select:

```text
POST /checkout
```

and watch:

```text
Browser
   ↓
API
   ↓
Authentication
   ↓
Checkout Controller
   ↓
Order Service
   ↓
Database
   ↓
Payment Service
   ↓
Stripe
   ↓
Queue
   ↓
Email Worker
```

Nodryl can explain each step.

Example:

```text
STEP 4 / 8

OrderService.createOrder()

Why?

The user has passed authentication.
The system now creates an order before requesting payment.

Source:
src/orders/service.ts:84
```

This turns architecture exploration into an interactive learning experience.

---

## 5.3 Debug

Nodryl should make debugging system-level problems easier.

Instead of reading hundreds of log lines:

```text

```

The developer sees:

```text

   ▼
```

Every major Nodryl feature should fall under one of these four categories.

> What exists?

Shows:

- services
- routes
- databases
- caches
- queues
- workers
- external APIs
- infrastructure
- dependencies

---

## Flow

> What is happening?

Shows runtime execution.

Examples:

- HTTP requests
- database queries
- queue events
- WebSocket activity
- API calls
- retries
- worker execution
- cron jobs

---

## Explain

> Why is this happening?

Provides context for:

- why a component was called
- what code caused the connection
- why a dependency exists
- what data is moving
- which file created the behavior

## Debug

> What went wrong?

Shows:

- errors
- failed requests
- latency
- bottlenecks
- retries
- broken dependencies

# 8. Presentation Philosophy

Presentation is a core part of Nodryl.

The visual experience should be one of the biggest reasons developers want to use it.

Nodryl should feel:

- beautiful
- calm
- readable
- alive
- informative
- fast
- polished
- cinematic without becoming distracting

The goal is not excessive animation.

The goal is meaningful animation.

Every visual movement should communicate something.

Examples:

| Visual behavior | Meaning |
|---|---|
| Moving pulse | request/event |
| Slow pulse | high latency |
| Red pulse | failure |
| Repeating pulse | retry |
| Purple pulse | async event |
| Node glow | active component |
| Faded node | inactive component |
| Expanding queue | backlog |
| Edge thickness | request volume |
| Edge animation speed | request speed |

# 11. Semantic Zoom

Semantic zoom is one of the most important Nodryl features.

Zoom should not simply make things physically larger.

It should change the **level of abstraction**.

## Level 1 — System

```text
Frontend
   ↓
Backend
   ├── Database
   ├── Redis
   └── Stripe
```

---

## Level 2 — Services

```text
Backend

├── Auth
├── Users
├── Orders
├── Payments
└── Notifications
```

---

## Level 3 — API Flow

```text
POST /checkout
   ↓
AuthMiddleware
   ↓
CheckoutController
   ↓
OrderService
   ↓
PaymentService
```

---

## Level 4 — Functions

```text
PaymentService.process()

├── calculateTotal()
├── createPaymentIntent()
├── saveTransaction()
└── publishEvent()
```

---

## Level 5 — Code

```text
stripe.paymentIntents.create({
    amount,
    currency
})
```

The developer should be able to move smoothly between these layers.

# 14. Replay

Replay should be a major Nodryl feature.

The developer can select a previous execution:

```text

```

```bash

```

The execution plays again visually.

Playback controls:

```text

0.5x
1x
2x
Instant
```

The developer can:

- pause
- inspect any step
- move forward
- move backward
- open source code
- inspect payloads
- inspect latency
- inspect errors

Replay connects Nodryl's three main purposes:

- understanding
- learning
- debugging

Possible evidence sources:

- AST
- imports
- route definitions

Nodryl should visually distinguish certainty.

Example:

This is important for developer trust.

# 20. Static Analysis

Static analysis determines what *can* happen.

It should detect:

- files
- imports
- functions
- classes
- routes
- models
- services
- external clients
- database usage
- configuration
- dependencies

Tree-sitter is a strong candidate.

Example:

```python
@app.post("/users")
def create_user():
    ...
```

becomes:

```text
POST /users
      ↓
create_user()
```

---

# 21. Runtime Instrumentation

Runtime tracing determines what *did* happen.

OpenTelemetry should be strongly considered.

Possible runtime events:

```text

function called
database query
cache lookup
HTTP request
queue publish
queue consume
exception
request completed
```

Each event becomes something Nodryl can animate.

# 39. Main Technical Challenges

## Accurate architecture extraction

This is the hardest core problem.

Software can contain:

- reflection
- dynamic imports
- metaprogramming
- runtime routing
- generated code

Nodryl should never pretend to understand what it cannot reliably detect.

---

## Visual scale

A large repository may contain:

- hundreds of modules
- thousands of functions
- thousands of edges

Semantic zoom and automatic grouping are mandatory.

---

## Performance

Runtime instrumentation must not significantly slow down applications.

---

## Framework support

Different frameworks represent architecture differently.

Adapters will require significant engineering.

---

## Noise

Too much runtime activity can turn the visualization into chaos.

Nodryl must aggressively:

- group
- filter
- summarize
- prioritize

System map appears.

### 20–40 seconds

### 40–60 seconds

- latency

- source locations

At this moment the user should think:

> "I finally understand what this application is doing."

# 46. Short Pitch

Modern developers increasingly build software with AI, but that makes it easier to lose track of what the system actually does.

Nodryl automatically maps your application and turns it into a live visual system.

When requests move through APIs, databases, caches, queues, workers, and external services, you can watch those interactions happen in real time.

You can zoom from the whole architecture down to an individual function, isolate requests, replay executions, inspect errors, and jump directly to the source code.

Nodryl helps developers:

**understand, learn, and debug their systems by watching them run.**
